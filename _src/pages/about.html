About Five Blocks

An open, plain-language guide to the computer science underneath Web3. It is written for developers and curious readers, not traders.

What it is

Five Blocks grew from a small set of research notes on Merkle trees, state machine replication, Byzantine faults, Ethereum and Chainlink. Each note became one page, ordered so that each idea builds on the one before.

It is educational only. Nothing here is investment, legal or tax advice, and the site doesn't show prices or link to exchanges.

How the chain works

Each page is a block. Its payload is the exact bytes of the original note or notes it was written from, served in data/. Its hash is:

hash = SHA-256( previous hash as 64 hex characters ‖ payload bytes )

Block #0's previous hash is 64 zeros:

{{genesis}}

The Verify button on the home page downloads every payload and recomputes all five hashes in your browser. To check from a terminal in a copy of the repository, run this for block #0, then repeat with each result as the next block's prefix:

( printf '%064d' 0; cat site/data/MerkleTree.yaml ) | sha256sum

The build refuses to run if a payload contains Windows line endings, and .gitattributes stops Git converting them, so the bytes and the hashes are the same on every machine.

What we corrected from the notes

The notes are kept unchanged as payloads. Where they were wrong or out of date, the pages say something different:

  • Byzantine faults. The notes say Lamport "proved the sufficiency of 3n using digital signatures". In the 1982 paper, signed messages allow agreement with any number of traitors. The 3f + 1 bound is for unsigned, oral messages.
  • State machine replication. The notes list 3 replicas "for fault detection". Comparing two copies is enough to detect a difference; 2f + 1 replicas are needed to outvote f faulty ones. The page also separates crash faults (2f + 1) from Byzantine agreement (3f + 1).
  • Merkle trees. A second-preimage attack forges a different set of leaves with the same root, not a different document. The fix is to prefix leaf and node hashes differently, as RFC 6962 does.
  • Ethereum. We dropped figures that date quickly: market rank, a 2023 client version, a 2023 node count and a 2016 throughput figure. The energy saving from The Merge is now the over 99.98% cited on ethereum.org, not 99%. Serpent, LLL and Mutan are retired.
  • Chainlink. It is no longer only "built on Ethereum": it runs on many chains. The notes' "election data" example is replaced with the main real use, price feeds.
  • Format. Ethereum.json and Chainlink.json contain // comment lines, which JSON does not allow, so standard JSON parsers reject them. They are kept as they are, because they are block payloads.
  • Unverified claims. We left out the notes' claims about submarines, airliners and spacecraft, because we could not confirm them from a primary source.

Sources

  • Lamport, Shostak and Pease, The Byzantine Generals Problem (1982), and Reaching Agreement in the Presence of Faults (1980; Dijkstra Prize 2005).
  • Fred Schneider, Implementing Fault-Tolerant Services Using the State Machine Approach (1990).
  • Leslie Lamport, Paxos Made Simple, and the Raft consensus algorithm.
  • Castro and Liskov, Practical Byzantine Fault Tolerance (1999).
  • RFC 6962, Certificate Transparency, and IPFS: Merkle DAGs.
  • Satoshi Nakamoto, Bitcoin: A Peer-to-Peer Electronic Cash System.
  • ethereum.org: white paper, EVM, gas, proof of stake, The Merge and energy consumption. EIP-20, EIP-721 and EIP-1559.
  • Chainlink white paper (2017) and Chainlink 2.0 (2021), Data Feeds and VRF documentation.

Contributing

Pages are HTML files in _src/pages/, and the chain order is in _src/blocks.json. Edit them, run python _src/build.py, and open a pull request on GitHub. Adding a new topic means adding its notes to site/data/ as a new block at the end of the chain.
