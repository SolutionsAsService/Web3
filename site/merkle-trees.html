A fingerprint for data

A cryptographic hash function turns any input, a word or a whole film, into a short, fixed-size output called a hash or digest. SHA-256, used throughout this site, always gives 256 bits, written as 64 hexadecimal characters.

A good hash function has these properties:

  • Deterministic. The same input always gives the same hash.
  • Avalanche. Change one character and about half the output bits flip. The new hash looks unrelated to the old one.
  • One-way. Given a hash, you cannot work back to an input that produces it (preimage resistance).
  • Collision-resistant. Nobody can find two different inputs with the same hash.

From one hash to a tree

To fingerprint a big data set, such as a block's transactions or the files in a download, you could hash it all at once. But then checking any one piece means downloading everything. Ralph Merkle's answer, from 1979, is to hash in a tree:

  1. Split the data into blocks and hash each one. These hashes are the leaves.
  2. Pair up neighbouring hashes, join each pair and hash it, to make the next level up.
  3. Repeat until one hash is left: the Merkle root.

The root commits to every leaf. Change one byte anywhere, and its leaf hash changes, then its parent, and so on, all the way to the root.

Leaves are hashed as SHA-256(0x00 ‖ record) and inner nodes as SHA-256(0x01 ‖ left ‖ right), the scheme from RFC 6962 explained below.

Proving one piece

To prove that a record is in the tree, you don't need the other records, only the hashes along its path. Hash the record, combine it with its sibling, combine that with the next sibling up, and see whether you arrive at the root you already trust.

The proof grows with the logarithm of the size. A tree with a million leaves needs only 20 sibling hashes, about 640 bytes. That is why a phone wallet can check that a transaction is in a Bitcoin block without downloading the block, a method the Bitcoin paper calls simplified payment verification.

Keeping leaves and branches apart

A naive Merkle tree has a weakness. An attacker can present an inner node's two child hashes as if they were a leaf, and so prove a "record" that was never in the data, with the same root. This is called a second-preimage attack.

The fix is to hash leaves and inner nodes differently. Certificate Transparency (RFC 6962) puts a 0x00 byte in front of every leaf and a 0x01 byte in front of every inner node, so a branch can never pass for a leaf. The tree above does the same.

Where Merkle trees are used

Bitcoin
Each block header holds the Merkle root of the block's transactions.
Ethereum
Uses a variant, the Merkle Patricia trie, to commit to every account's state in each block header.
Git
Every commit, folder and file is named by its hash, forming a Merkle graph: the commit hash commits to the whole project history.
IPFS
Files are split into blocks and linked in a Merkle DAG, so content is addressed by what it is, not where it lives.
Certificate Transparency
Public logs of every TLS certificate, provably append-only.
File systems and databases
ZFS and Btrfs checksum data in trees, and Cassandra and Dynamo-style databases compare Merkle trees to find replicas that disagree.

And this site: each page's hash covers its source files and the hash before it, which is a hash chain, the simplest relative of a Merkle tree.
